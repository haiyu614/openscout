# OpenScout 项目定位文档

> 项目名为暂定名。本文用于确定产品方向和首版边界，不作为最终技术设计。

## 1. 一句话定位

OpenScout 是一个依附通用 Agent 运行的持续开源发现与贡献助手：它根据用户的自然语言需求，在 GitHub 上寻找合适的开源项目和可解决的 Issue；用户关注仓库后，可创建定时任务，按指定频率和数量持续扫描 Issue、生成本地 PR 草案，并通过去重机制避免重复劳动；每个 PR 草案都支持多轮对话修改，只有在用户明确批准后才执行 fork、push 和创建远端 PR。

## 2. 要解决的问题

用户参与开源通常要经历一条割裂且成本较高的流程：

1. 将模糊需求转换为 GitHub 搜索条件；
2. 从大量仓库中判断哪些项目真正匹配；
3. 识别仍然有效、范围合适且可贡献的 Issue；
4. 阅读仓库规范、搭建环境并理解相关代码；
5. 修改代码、补充测试并验证结果；
6. 按项目要求准备提交信息和 PR 描述；
7. fork、推送分支并创建 PR。

现有通用 Agent 擅长处理已给定仓库内的编码任务，但通常不负责从开放的 GitHub 生态中主动发现目标，也缺少跨仓库筛选、贡献可行性判断和安全审批闭环。

OpenScout 的价值是把“发现合适目标”和“完成一次可审阅的贡献”连接起来，同时保留用户对外部写操作的最终控制权。

## 3. 目标用户

### 3.1 主要用户

- 有明确技术需求，希望寻找可直接采用的开源项目的开发者；
- 希望参与开源，但不熟悉项目筛选和贡献流程的开发者；
- 希望持续寻找适合自身技术栈、能力范围或兴趣方向 Issue 的贡献者；
- 维护内部技术选型或开源协作流程的研发团队。

### 3.2 用户前提

首版默认用户具备以下条件：

- 能够审阅代码 diff 和测试结果；
- 拥有可用于 GitHub API 的授权；
- 理解批准后将代表自己执行 fork、push 和创建 PR；
- 愿意对最终提交内容承担责任。

OpenScout 不把“完全不懂代码也能自动向任意项目提交 PR”作为首版目标。

## 4. 核心价值

### 4.1 找得准

不仅基于关键词匹配，还要结合仓库活跃度、技术栈、许可证、维护状态、Issue 状态、贡献规范和任务复杂度，对候选结果进行解释性排序。

### 4.2 做得完

不止推荐仓库或罗列 Issue，而是继续完成仓库分析、修改、测试和 PR 草案，交付一个可供用户审阅的本地贡献包。

### 4.3 推得安全

审批前不执行任何 GitHub 写操作。只有用户查看本地 diff、测试结果、风险说明和 PR 文案并明确同意后，系统才允许 fork、push 和创建 PR。

### 4.4 可依附通用 Agent

项目不重复构建完整的编码 Agent，而是复用宿主 Agent 的代码理解、编辑、命令执行和上下文管理能力。首版优先接入 DSH，核心能力与宿主适配层保持分离，为后续适配 OpenCode、Codex、CLI 或 MCP 保留空间。

## 5. 产品范围

### 5.1 场景 A：按需求寻找开源项目

用户输入自然语言需求，例如技术目标、运行环境、语言偏好、许可证要求或维护活跃度要求。

系统输出：

- 排序后的候选仓库；
- 每个候选的匹配理由和不匹配项；
- 关键事实，包括技术栈、许可证、活跃度、社区规模和最近维护情况；
- 采用风险与建议验证步骤；
- 可选的后续动作：进一步分析某个仓库，或寻找该仓库内适合贡献的 Issue。

### 5.2 场景 B：寻找可贡献的 Issue

用户可以从全 GitHub、指定主题或已选仓库中寻找 Issue。

系统输出：

- Issue 与用户目标、技术栈和能力范围的匹配度；
- Issue 是否仍然有效、是否已有认领或相关 PR；
- 预计影响范围、实现难度和验证成本；
- 仓库贡献门槛与潜在阻塞项；
- 推荐处理顺序及理由。

### 5.3 场景 C：生成本地贡献包

用户选定 Issue 或明确提出贡献目标后，系统调用宿主 Agent：

1. 克隆目标仓库或准备隔离工作区；
2. 阅读许可证、贡献指南、Agent 指令和相关文档；
3. 定位相关代码与测试；
4. 形成实施方案；
5. 修改代码并执行必要验证；
6. 生成本地 diff、测试结果、变更摘要、风险说明、提交信息建议和 PR 文案。

此阶段不执行 GitHub 写操作。

### 5.4 场景 D：批准后发布贡献

用户明确批准本地贡献包后，系统才可以：

1. 检查 GitHub 授权和目标仓库当前状态；
2. fork 目标仓库，或复用用户已有 fork；
3. 创建贡献分支并推送提交；
4. 向上游仓库创建 PR；
5. 返回 PR 地址和实际执行记录。

首版默认创建 Draft PR，以便用户和维护者继续检查；是否允许直接创建 Ready for review PR 作为后续配置项。

### 5.5 场景 E：创建持续扫描任务

当用户确认关注一个或多个开源仓库后，可以将一次性搜索保存为长期任务。任务至少包含：

- 任务名称与关注仓库集合；
- Issue 标签、关键词、语言、难度、时间范围等筛选条件；
- 扫描频率、时区、生效时间和暂停状态；
- 每次运行最多扫描的 Issue 数量；
- 每次运行、每天或每周最多生成的本地 PR 草案数量；
- 最大并发生成数量和失败重试策略；
- 自动忽略规则及用户手工排除项。

每次任务运行时，系统从上次成功扫描的水位继续获取新增或发生关键变化的 Issue，完成去重、可行性预检和排序，然后只为配额内的高优先级 Issue 创建 PR 工作项。定时任务可以自动生成本地贡献包，但不能绕过用户审批执行 fork、push 或创建远端 PR。

用户可以随时暂停、恢复、修改或终止任务。修改仓库范围、过滤条件、频率或配额后，只影响后续运行，不应自动复活已删除、已关闭或已明确忽略的 PR 工作项。

### 5.6 场景 F：围绕 PR 工作项持续协作

每个准备中的贡献都作为独立的 PR 工作项维护，而不是一次性输出。工作项保存目标仓库、Issue、工作区、分支、diff 版本、验证结果、PR 文案、对话历史、审批记录和远端 PR 状态。

在本地草案阶段，用户可以围绕某个 PR 工作项进行多轮对话，例如：

- 要求调整实现方案或缩小改动范围；
- 修改代码、测试、提交信息、PR 标题或正文；
- 解释某段 diff 或验证失败；
- 放弃当前版本并回退到此前版本；
- 删除尚未发布的 PR 草案。

每次实质性修改都必须生成新版本、重新执行受影响的验证，并使此前审批失效。用户批准的必须是一个确定的 diff 和 PR 文案版本。

远端 Draft PR 创建后仍可继续多轮对话。代码变化先在本地形成新版本并重新验证，用户批准后才允许向原 PR 分支追加提交；只修改 PR 标题或正文时，也要展示新旧差异并单独确认后再调用 GitHub 写接口。系统不得因用户曾批准创建 PR，就自动获得后续修改该 PR 的持续授权。

对于已经创建到 GitHub 的 PR，“删除”不能承诺为真正删除远端 PR：产品语义应是关闭 PR，并在用户再次确认后选择是否删除 fork 中的对应分支；本地工作项保留最小审计记录并标记为已关闭。尚未发布的本地草案可以删除工作区和生成物，但应保留去重所需的墓碑记录，防止下一次扫描立即重复生成。

## 6. 标准工作流

```text
用户描述需求
  ↓
搜索仓库并展示证据
  ↓
用户确认关注仓库
  ├─ 一次性继续：立即扫描 Issue
  └─ 持续关注：创建任务并设置频率、配额和过滤条件
                    ↓
              调度器触发任务运行
                    ↓
       增量扫描 → 去重 → 预检 → 排序
                    ↓
           为配额内 Issue 创建 PR 工作项
                    ↓
       隔离工作区内分析、修改和测试
                    ↓
              生成本地贡献包
                    ↓
       用户与该 PR 工作项进行多轮对话
          ├─ 修改：生成新版本并重新验证
          ├─ 删除：丢弃本地草案并写入去重墓碑
          └─ 批准：绑定当前版本进入发布阶段
                    ↓
          重新检查远端状态、重复项与权限
                    ↓
          fork → branch → push → create Draft PR
                    ↓
        继续修改 / 关闭 PR / 等待维护者处理
```

任何一步都允许用户停止、修改约束或切换候选。任务停止不应自动删除已生成的 PR 工作项；PR 工作项的修改、批准、发布、关闭与删除拥有独立生命周期。

### 6.1 核心对象与状态

#### 任务 Task

代表用户对一组仓库的持续关注和自动化策略，建议至少具有：`DRAFT`、`ACTIVE`、`PAUSED`、`STOPPED`、`ERROR` 状态。任务负责调度和配额，不直接等同于某次扫描或某个 PR。

#### 任务运行 Task Run

代表任务的一次实际触发，记录计划时间、扫描水位、候选 Issue、去重结果、配额消耗、生成结果和失败原因。任务运行应可重试，但重试必须复用同一运行标识和去重记录，不能重复创建 PR 工作项。

#### PR 工作项 PR Work Item

代表从某个 Issue 到本地草案再到远端 PR 的完整生命周期，建议至少具有：`CANDIDATE`、`GENERATING`、`REVIEW`、`APPROVED`、`PUBLISHING`、`PUBLISHED`、`REVISING`、`DISCARDED`、`CLOSED`、`FAILED` 状态。每次修改形成独立版本，审批绑定到具体版本。

### 6.2 去重规则

去重应同时覆盖系统内部记录和 GitHub 远端事实：

1. **Issue 主键去重**：以 GitHub 仓库不可变 ID 与 Issue 不可变 ID 作为首要键，不能只依赖 URL、仓库名或 Issue 标题；
2. **跨任务去重**：同一用户的多个任务命中同一 Issue 时，只允许存在一个活跃 PR 工作项，其余任务记录为重复命中；
3. **运行幂等**：调度重试、超时恢复和并发执行必须通过唯一约束或租约避免重复生成；
4. **远端去重**：生成前和发布前检查关联 PR、Issue 时间线、用户已有分支和系统已发布记录；
5. **意图去重**：没有明确 Issue 的主动贡献，以仓库、目标基线、规范化贡献意图和改动指纹组合判断重复；
6. **墓碑去重**：用户删除或拒绝的工作项保留最小记录。默认不再次生成，除非用户明确恢复，或 Issue 出现足以改变结论的关键更新；
7. **版本去重**：PR 多轮修改属于同一工作项的新版本，不创建新的工作项，也不重复占用任务的 PR 数量配额；
8. **发布前终检**：如果发现维护者或其他贡献者已经提交等价修复，应中止发布并要求用户决定关闭、重新规划或继续。

## 7. 产品原则

### 7.1 证据优先

仓库和 Issue 推荐必须附带可核验的来源与判断依据。不能只给出模型生成的笼统结论，也不能把缺失信息包装成确定事实。

### 7.2 人在回路

用户对以下动作拥有最终决定权：

- 确认关注哪些仓库，并设置任务频率和生成配额；
- 选择、忽略、恢复或删除 PR 工作项；
- 通过多轮对话接受或修改实施方案和本地代码；
- 批准某个确定版本的贡献包；
- 批准任何 GitHub 写操作；
- 关闭已发布 PR 及删除远端分支。

定时任务可以无人值守地扫描 Issue 和生成限额内的本地 PR 草案，但首版不支持无人值守地向公开仓库批量提交远端 PR。

### 7.3 最小权限

搜索、定时扫描和本地草案生成阶段只申请 GitHub 只读权限。写权限应延迟到单个 PR 工作项的发布阶段，并限制在完成 fork、push、创建或关闭 PR 所需的最小范围。一个 PR 的批准不能授权其他 PR 或后续任务运行。

### 7.4 尊重项目规则

在修改代码前必须检查目标仓库中的许可证、贡献指南、行为准则、Issue/PR 模板以及仓库内 Agent 指令。如果规则冲突、许可证不明确或项目禁止相关贡献，系统应停止并向用户说明原因。定时任务应在每次生成前重新检查可能变化的贡献规则。

### 7.5 质量高于数量

任务中的“PR 数量”是资源上限，不是必须完成的产量目标。若没有足够高质量且不重复的 Issue，本次运行可以生成零个 PR 草案。系统应避免无意义格式化、重复修复、低价值批量 PR 和未经验证的改动。

### 7.6 宿主解耦

GitHub 检索、候选评分、任务状态、审批门禁和发布逻辑应形成独立核心；DSH 只负责提供 Agent 能力和交互入口。不得让核心业务直接依赖某个宿主的私有会话格式。

## 8. 首版产品边界

### 8.1 已确认范围

- 平台：仅 GitHub；
- 宿主：优先 DSH；
- 目标：同时支持项目发现和 Issue 贡献；
- 仓库：允许处理任意公开仓库；
- 审批产物：本地 diff、测试结果和 PR 文案；
- 写操作：必须在用户明确批准单个 PR 工作项的确定版本后执行；
- 发布路径：默认通过用户 fork 提交到上游仓库；
- 任务：支持关注多个仓库、定时扫描、配额控制、暂停恢复和运行记录；
- 去重：覆盖跨任务、任务重试、本地工作项和远端已有 PR；
- PR 协作：支持围绕单个 PR 工作项多轮修改、重新验证、删除本地草案和关闭远端 PR；
- 执行方式：单用户可维护多个任务；每个任务允许受控并发，但必须满足去重和配额约束。

### 8.2 首版不做

- GitLab、Gitee 等其他代码托管平台；
- 无人值守批量认领 Issue 或批量创建远端 PR；
- 自动读取维护者评论后无人值守地修改并推送 PR；
- 自动合并 PR；
- 绕过仓库权限、分支保护或贡献规范；
- 对所有编程语言和构建系统提供同等程度的环境保障；
- 社交排名、贡献积分或开发者撮合市场；
- 取代通用 Agent 的代码编辑和推理能力。

## 9. 与通用 Agent 的关系

OpenScout 是通用 Agent 的“开源发现与贡献工作流层”，而不是另一个通用编码 Agent。

### OpenScout 负责

- 将用户需求转换为 GitHub 检索计划；
- 聚合并规范化仓库、Issue 和 PR 信息；
- 候选过滤、评分、去重和解释；
- 贡献可行性预检；
- 持久化关注任务并按频率、时区和配额触发扫描；
- 管理任务、任务运行和 PR 工作项三层状态；
- 维护 PR 工作项的多轮对话、版本、验证和删除/关闭语义；
- 生成和展示审批材料；
- 审批后执行 GitHub 发布动作；
- 保存必要的审计和去重记录。

### DSH 或其他宿主 Agent 负责

- 理解目标代码库；
- 搜索符号和调用关系；
- 编辑代码；
- 运行命令、测试和静态检查；
- 根据反馈迭代实现。

DSH 的实际插件、工具、Skill、Hook 或 MCP 接口尚需基于现有代码和文档调研后确定，本文不预设不存在的扩展能力。

## 10. 建议的逻辑模块

以下是产品层面的模块边界，不代表最终目录结构：

1. **Intent Parser**：提取功能需求、技术栈、许可证、活跃度、难度和排除条件；
2. **GitHub Search Provider**：封装仓库、Issue、PR、用户 fork 和权限相关查询；
3. **Candidate Ranker**：基于硬过滤、可解释规则和语义相关性排序；
4. **Task Store**：持久化任务配置、关注仓库、过滤条件、频率、时区、配额和状态；
5. **Scheduler**：触发任务运行，管理扫描水位、并发限制、重试和配额窗口；
6. **Dedup Registry**：维护 Issue 主键、任务命中、工作项、远端 PR、租约和墓碑记录；
7. **Contribution Preflight**：检查 Issue 有效性、重复 PR、仓库规则、许可证和环境门槛；
8. **PR Work Item Manager**：维护每个贡献的状态、对话、版本、审批和删除/关闭语义；
9. **Agent Orchestrator**：将选定工作项交给 DSH，并约束执行阶段和可用工具；
10. **Workspace Manager**：创建隔离工作区，管理上游仓库、fork 和分支状态；
11. **Validation Collector**：收集测试、lint、构建结果以及无法执行的验证项；
12. **Review Bundle Builder**：生成带版本标识的 diff、变更摘要、风险说明、提交建议和 PR 草案；
13. **Approval Gate**：验证用户批准对象与当前版本一致，任何实质修改后自动撤销旧审批；
14. **GitHub Publisher**：批准后执行 fork、push、创建或关闭 PR 以及可选的分支删除；
15. **Audit Log**：记录关键读取依据、任务运行、用户决策和外部写操作结果；
16. **DSH Adapter**：将核心工作流暴露给 DSH，并复用其 Agent 执行和多轮会话能力。

## 11. 安全与信任边界

### 11.1 外部仓库内容不可信

README、Issue、评论、源码和仓库内 Agent 指令都可能包含恶意提示或命令。系统必须把这些内容视为数据，不能让它们自行扩大权限、读取无关凭据或跳过审批。

### 11.2 本地命令具有风险

构建脚本、测试脚本和依赖安装可能执行任意代码。首版至少需要：

- 独立临时工作区；
- 明确展示待运行命令；
- 限制环境变量和凭据暴露；
- 设置超时和资源限制；
- 对高风险命令继续请求确认；
- 不向目标仓库进程暴露 GitHub 写凭据。

是否采用容器、虚拟机或宿主现有沙箱，需要在技术设计阶段结合 DSH 能力决定。

### 11.3 审批必须绑定具体内容

用户批准的对象应包含：

- 仓库与目标分支；
- Issue；
- commit/diff 内容摘要及不可变标识；
- 已执行和未执行的验证；
- PR 标题与正文；
- 计划执行的远端动作。

如果批准后代码、目标分支或 PR 内容发生实质变化，原批准应失效并要求重新审阅。

### 11.4 发布前重新校验

批准与发布之间，上游分支、Issue 状态、已有 PR 或贡献规则可能变化。发布前必须重新检查；出现冲突时停止发布，而不是擅自 rebase、覆盖或改换目标。

## 12. 候选排序原则

首版建议将排序拆成两层：

### 12.1 硬过滤

- 仓库可访问且未归档；
- 许可证满足用户要求或明确标记为未知；
- 主要语言和运行环境满足约束；
- Issue 仍处于开放状态；
- 不存在明确重复 PR；
- 不违反用户排除条件。

### 12.2 可解释评分

- 与用户需求的相关性；
- 近期维护活跃度；
- 文档和贡献规范完整度；
- Issue 描述清晰度；
- 预计实现与验证成本；
- 是否适合首次贡献；
- 维护者近期响应情况；
- 与用户技能和时间预算的匹配度。

评分只能辅助排序，必须同时展示原始事实和不确定项，避免把单一分数伪装成客观结论。

## 13. MVP 验收标准

一次完整演示应能够：

1. 接收一段自然语言需求和若干约束；
2. 返回有证据、有排序理由的仓库候选；
3. 让用户关注多个仓库并创建带频率、时区、过滤条件和 PR 数量上限的任务；
4. 手动或定时触发任务运行，从扫描水位增量获取可贡献 Issue；
5. 对候选完成跨任务、跨运行和远端 PR 去重；
6. 对配额内的选定 Issue 完成规则与可行性预检；
7. 在隔离工作区中调用 DSH 完成小范围代码修改和必要验证；
8. 向用户展示带版本标识的完整本地贡献包；
9. 支持用户通过至少两轮对话修改同一 PR 工作项，并证明旧审批或旧版本不会被误发布；
10. 支持删除未发布草案，且下一次任务运行不会立即为同一 Issue 重复生成；
11. 在未批准时证明系统没有执行 GitHub 写操作；
12. 在用户批准当前版本后完成 fork、push 和创建 Draft PR；
13. 支持关闭已发布 PR，并明确区分关闭 PR 与删除远端分支；
14. 输出任务、任务运行和 PR 工作项三级可追踪记录，并能清楚说明失败发生在哪一步。

## 14. 成功指标

首版不以 PR 数量为首要指标，建议关注：

- 候选仓库中被用户认为相关的比例；
- 持续任务按计划触发的成功率和扫描水位正确率；
- 推荐 Issue 被用户选择继续处理的比例；
- 重复 Issue、重复运行和远端等价 PR 的拦截率及误判率；
- 每个配额窗口实际生成数量是否严格不超过用户上限；
- 进入编码阶段后成功生成可审阅贡献包的比例；
- 自动验证成功率及验证覆盖说明完整度；
- PR 工作项经过多轮修改后获得用户批准的比例；
- 用户批准后成功创建 PR 的比例；
- 因重复工作、规则冲突或环境不可用而在编码前被正确拦截的比例；
- 审批前发生 GitHub 写操作的次数，目标必须为零；
- 用户手工修订 diff 和 PR 文案的程度；
- 维护者关闭为低质量、无关或重复 PR 的比例。

## 15. 主要风险

| 风险 | 影响 | 首版应对 |
|---|---|---|
| GitHub 搜索结果噪声大 | 推荐不可信 | 硬过滤、证据展示、允许用户快速调整约束 |
| Issue 已被处理但状态未更新 | 重复贡献 | 搜索关联 PR、分支和近期评论，编码前与发布前各检查一次 |
| 仓库内容触发提示注入 | 泄露凭据或越权 | 不可信内容隔离、最小权限、工具白名单、审批门禁 |
| 运行恶意构建脚本 | 本地环境受损 | 隔离执行、隐藏凭据、命令确认和资源限制 |
| 自动修改质量不足 | 产生低质量 PR | 小任务优先、测试要求、本地审阅、默认 Draft PR |
| 不同项目构建方式差异大 | 验证不稳定 | 首版限制验证承诺，明确区分已验证和未验证项 |
| DSH 扩展点不满足流程 | 集成成本增加 | 先调研实际接口，核心与适配层解耦，必要时通过 CLI/MCP 过渡 |
| GitHub API 限流或授权失败 | 流程中断 | 缓存只读结果、显示限流状态、支持安全重试和断点恢复 |
| 定时任务重入或失败重试 | 重复工作项和资源浪费 | 任务运行幂等键、分布式租约、唯一约束和可恢复扫描水位 |
| 多任务命中同一 Issue | 重复生成多个 PR 草案 | 用户级 Issue 唯一索引、工作项复用和重复命中记录 |
| 配额被并发执行穿透 | 超出用户数量与成本预期 | 原子预占配额、完成后结算、失败释放并设置并发上限 |
| 删除草案后被再次生成 | 用户反复收到相同结果 | 保留墓碑及原因，只有显式恢复或关键事实变化后才重新评估 |
| 多轮修改后误用旧审批 | 发布用户未批准的内容 | 版本化贡献包，任何实质修改自动撤销审批 |
| 上游在审批后发生变化 | diff 过期或冲突 | 发布前重新校验，变化后中止并重新审批 |
| 自动化贡献引发社区反感 | 项目声誉受损 | 限制自动化只生成本地草案、遵守贡献规范、强调用户责任和质量门槛 |

## 16. 差异化定位

OpenScout 不只是：

- GitHub 搜索界面：它需要完成从发现到贡献草案的闭环；
- Issue 推荐器：它需要验证任务是否仍可做，并进入真实代码工作；
- 自动 PR 机器人：它强调本地审阅、用户批准和社区质量；
- 新的编码 Agent：它复用 DSH 等通用 Agent，不重复建设底层代码能力；
- 无人值守贡献农场：它反对以数量为目标的低质量自动提交。

其核心差异是：**以证据驱动的目标发现、以通用 Agent 完成实现、以不可绕过的人工审批控制发布。**

## 17. 后续待确认

以下问题不阻塞项目定位，但会影响 MVP 技术方案：

1. 首版支持的语言和构建生态，是只保证 Python/TypeScript，还是接受任意仓库但降低验证承诺；
2. 任务频率支持固定间隔、Cron、自然语言周期中的哪些形式，以及最小允许间隔；
3. PR 数量上限按单次、每日、每周还是多种窗口同时约束，失败草案是否占用配额；
4. 删除/拒绝墓碑的默认保留期限，以及什么变化可以自动解除去重；
5. GitHub 授权采用 GitHub App、OAuth App、细粒度 PAT，还是复用 DSH 已有凭据机制；
6. DSH 实际提供哪些插件、工具、Skill、Hook、MCP、调度、持久化、沙箱和审批接口；
7. 首版是否需要语义检索或向量索引，还是先用 GitHub 查询、规则过滤和 Agent 复核；
8. 任务列表、运行记录、PR 工作项及多轮对话的交互形态，是终端、Web 面板，还是 DSH 原生会话；
9. 远端 PR 修改是否每次都要求单独批准，以及 PR 标题/正文小改动能否采用更轻量的确认方式；
10. 发布时默认 Draft PR 是否作为不可更改策略；
11. 任务状态、扫描水位、对话和工作区如何持久化，以及失败后支持何种粒度的断点恢复；
12. 项目名称、许可证和代码仓库组织方式。
